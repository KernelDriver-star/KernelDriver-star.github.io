CUDA-GDB 使用指南：GPU 内核调试从入门到实践

Created2026-09-16|Updated2026-09-16|CUDA
|Post Views:

写 CUDA 代码最痛苦的莫过于——CPU 端跑得好好的，一到 GPU 上就段错误、结果不对或者干脆卡死，printf 大法既慢又难定位。cuda-gdb 是 NVIDIA 官方提供的 GPU 源码级调试器，基于 GDB 扩展，能让你像调 CPU 程序一样在 GPU 内核里打断点、单步、查看变量。这篇整理一下实际开发中常用的流程和命令。

一、环境准备

1.1 前置条件

  • 安装 CUDA Toolkit（自带 cuda-gdb，不需要单独装）
  • GPU 驱动版本 ≥ CUDA 版本对应要求
  • Linux 环境（cuda-gdb 对 Linux 支持最完整，Windows 下功能有限）
  • 编译时加 -G 选项生成调试信息（关键！）

1.2 验证安装

1.3 编译带调试信息的 CUDA 代码

选项 作用
-G 生成 GPU 端调试信息（device code debugging），必须加
-g 生成 CPU 端调试信息（host code debugging）
-O0 关闭优化，避免变量被优化掉导致打印不出值

坑点：-G 和 -lineinfo 不是一回事。-G 生成完整调试信息（可断点、可查值），-lineinfo 只保留行号映射（用于栈回溯，不能查变量值）。调试阶段用 -G，发布阶段保留 -lineinfo 即可。

5.2 调一个段错误 / 非法内存访问

非法访问通常在 cudaDeviceSynchronize 后才报出来，定位不了具体行。两种办法：

方法一：用 cuda-memcheck 先定位

它会打印出错的内核名、线程坐标、访问地址，拿到这些信息再去 cuda-gdb 里精确定位。

方法二：用条件断点逐线程排查

提示：非法访问最常见的根因是越界，先用 cuda warp print idx 批量看一眼线程算出的索引范围，一眼就能发现超界的那个。

5.3 调一个卡死的内核

内核死循环或者死锁，程序卡住不动。这种情况下 cuda-gdb 可以在运行中按 Ctrl+C 中断，查看所有线程当前停在哪一行：

死锁的典型场景：warp 内某个分支永不收敛（不同线程走了不同路径但都依赖彼此同步）。用 cuda warp list 看 warp 是否都卡在同一行，如果散落各处说明控制流没对齐。

七、常见坑

现象 原因 解决
No CUDA devices found 驱动版本太低 / 没独占 GPU 升级驱动，确保没有其他进程占用 GPU
变量值显示 <optimized out> 用了 -O2 优化 重新用 -G -g -O0 编译
断点命中后”焦点不对，变量值像别的线程的” cuda-gdb 焦点默认在 warp 头个线程 cuda focus 查看后用 cuda focus block(x,y,z), thread(a,b,c) 切换
printf 在内核里没输出 未 cudaDeviceSynchronize 在启动后加 cudaDeviceSynchronize()
调试时性能极慢 默认单 warp 推进 调试阶段用小数据量（grid/block 都调小）
-G 编译后结果不一样了 -G 会关闭部分优化 用 -lineinfo 替代做”轻量调试”，或用复现最小用例

八、速查表

命令 作用
cuda focus 查看当前 GPU 焦点
cuda focus <sm>,<warp>,<lane> 切换焦点
cuda focus block(x,y,z), thread(a,b,c) 按逻辑坐标切换
cuda warp print <var> 批量打印整个 warp 的变量
cuda thread print <expr> 打印当前线程的表达式
cuda block list / cuda thread list 列出活跃 block / thread
info cuda state GPU 当前状态
info cuda kernels 正在执行的内核
set cuda launch_blocking on 异步变同步，便于捕获内核
break <kernel> if threadIdx.x == N 条件断点定位单线程

小结

cuda-gdb 的核心思路就一句话——先定位到出问题的具体线程，再像调 CPU 一样单步看变量。难点在于 GPU 的并行性让你需要先用 cuda focus / cuda warp list 弄清楚当前在跟哪一个线程对话。

日常开发建议这么用：

  1. 用 compute-sanitizer / cuda-memcheck 快速定位出错内核和线程；
  2. 进 cuda-gdb，用条件断点锁定到那个线程；
  3. 单步 + print 查变量；
  4. 用 cuda warp print 批量看 warp 内所有线程的值，一眼发现异常。

写内核调试这种事情，熟能生巧，多用几次 cuda warp print 你会发现 GPU 里”有一个线程算错了”这种 bug 比想象中好定位得多。
